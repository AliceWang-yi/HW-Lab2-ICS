# Lab2 -- BombLab

> 2026 秋季学期。实验领取地址、截止时间及迟交规则以课程公告为准。

## 一、实验简介

CSAPP 第三章配套实验。

这次实验需要你综合运用 x86-64 汇编、Linux、GDB 和 C 语言，分析一个没有源码的程序，弄清楚它到底在算什么。

实验分为两部分：

- `tutor/`：独立的 Phase 0 调试教程，帮助你熟悉 GDB，不计分。
- `bomb`：属于你的二进制炸弹，包含六个正式关卡和一个选做的隐藏关。

你的目标是拆除六关，并把分析得到的解法写进 `defuser.c`。

与只提交一份密码的 BombLab 不同，这次炸弹会给出一个输入数值 challenge，口令随它变化。你需要写出从 challenge 算出口令的程序。助教会换一批输入测试，因此一次运行成功，还不代表这一关已经完成。

## 二、实验内容

### Phase 0：调试教程

这一部分提供源码和参考解法。你可以对照 C 代码，练习设置断点、查看寄存器、读取内存和单步执行，再看同一段代码如何变成汇编。

在学生仓库根目录运行：

```sh
make -C tutor test
```

也可以使用 `make test-phase0`。具体练习见 `tutor/README.md`。教程不需要填写学号，也不需要下载个人炸弹，建议先做一遍再开始正式六关。

### 正式六关

每关都会检查你输入的一行口令。输入正确会显示通关提示；错误则输出 `BOOM!!!` 并退出。

不用担心，爆炸不会扣分，也不会被记录。分析过程中可以反复运行。

| 关卡 | 主要知识点 | 一行口令中的整数个数 |
| --- | --- | :---: |
| 第 1 关 | 函数调用、参数传递、返回值 | 1 |
| 第 2 关 | 数组、循环、递推关系 | 6 |
| 第 3 关 | switch 分支与跳转表 | 2 |
| 第 4 关 | 递归调用与返回过程 | 1 |
| 第 5 关 | 结构体布局、指针、链表遍历 | 2 |
| 第 6 关 | 函数指针表与间接调用 | 1 |
| 隐藏关 | ████ | — |

六关可以分别调试，遇到暂时想不通的地方，可以先看另一关，不需要在 `config.txt` 中设置跳题。

每个人的炸弹都由助教按学号生成。各关考点相同，具体的常量、运算和数据布局可能不同；分析别人的炸弹，不能替代分析自己的炸弹。

## 三、实验步骤

### 1. 领取仓库和炸弹

从课程公布的学生模板创建自己的仓库。仓库放在自己的 GitHub 账号下，名称使用 `ics-2026-bomblab`，助教会按这个名字收作业。如果课程另行通知领取方式，按通知操作。

环境要求：Linux x86-64，安装 GCC、GNU Make、Python 3.10+、GDB 和 binutils（其中包含 `objdump`）。不要直接在无法运行 x86-64 Linux 程序的环境中尝试执行炸弹。

克隆后，在 `config.txt` 中填写自己的学号。例如：

```text
student_id = 24307130175
```

示例是演示账号，请替换成自己的学号。学号为 11 位数字或英文字母；含字母的学号如 `2580XH10083` 直接填写，保留大小写和前导零，不要转成数字。

然后下载炸弹：

```sh
make bomb
```

如果不能在线下载，到课程公布的学生模板仓库 Releases 页面下载自己的 `bomb-<学号>.tar.gz`，再用下面的命令导入。命令中的文件名换成实际下载的文件名：

```sh
python3 fetch_bomb.py --file bomb-24307130175.tar.gz
```

请核对学号。评分时使用的是课程名单中与你的 GitHub 账号绑定的炸弹，不会因为修改 `config.txt` 而换题。

领取成功后，已有炸弹的编译、运行和测试不再需要配置中的学号。你可以保留配置，也可以清空学号或删除 `config.txt`；是否提交学号不影响评分。只有重新领取炸弹时，才需要再次填写配置。为了让 GitHub Actions 自测，把个人 `bomb` 一并提交；`package.json` 不需要提交。

模板默认忽略下载和编译产物，首次领取炸弹后需要执行一次：

```sh
git add -f bomb
```

自己的 `bomb` 不需要修改。它只用于仓库中的公开自测，教师评分使用教师保存的副本。

### 2. 先固定一个输入，观察程序

以第 2 关为例：

```sh
./bomb --seed 42 --phase 2
```

程序会打印本关的 challenge，并等待输入。

`--phase 2` 表示只运行第 2 关；不指定 `--phase` 时，依次运行六关。`--seed` 用来生成本次的 challenge：同一个 seed 和关卡对应同一个 challenge，适合反复调试；换一个 seed，就可以检查解法是否适用于另一组输入。

调试开始时先固定 seed，不要每运行一次就换输入，否则不容易比较前后的观察结果。

### 3. 用反汇编和 GDB 分析

先导出本关的汇编：

```sh
objdump -d --disassemble=phase_02 ./bomb > phase_02.S
```

再用 GDB 运行：

```sh
gdb --args ./bomb --seed 42 --phase 2
```

在 GDB 中设置断点并开始执行：

```text
(gdb) break *phase_02
(gdb) run
```

程序等待口令时，可以先按本关要求的字段数输入几个数。即使答案不正确，也可以在进入关卡函数时停下来观察；不必先猜中答案才能调试。

结合汇编和运行结果，弄清楚输入是如何参与计算的、程序在哪里判断对错。每关的函数名是 `phase_01` 至 `phase_06`。更具体的观察方向见 `docs/gdb-phases.md`。

### 4. 把分析结果写成解法

所有正式解法都写在 `defuser.c` 中。例如，第 2 关对应接口：

```c
int solve_phase_2(uint64_t challenge, char *out, size_t cap);
```

你需要根据 challenge 算出口令，把它写入 `out`，不超过 `cap` 指定的缓冲区大小。函数成功时返回 0；尚未完成或发生错误时返回非零。

这里写的是从汇编恢复出的计算过程，不是某个 seed 对应的固定答案。

口令格式如下：

- 使用无符号十进制整数，以空格分隔；范围为 0 至 4294967295。
- 字段数按关卡要求填写，不能多写数字或附加文字。
- 写入 `out` 的字符串以 `\0` 结尾，不包含换行。
- 调试信息写到 stderr，不要输出到 stdout，否则会混入口令。
- 注意汇编中的操作宽度。32 位无符号加、减、乘等运算会按模 2³² 回绕，不要把它们当成无限精度计算。

不用修改 `defuser_main.c` 等驱动文件。评分时只取你的 `defuser.c`，与助教保存的驱动程序一起编译。

### 5. 验证，再换一个输入

编译解法：

```sh
make
```

用刚才的 seed 检查第 2 关：

```sh
./defuser --seed 42 --phase 2 | ./bomb --seed 42 --phase 2
```

管道两边的 seed 和关卡需要一致。左边生成口令，右边检查口令。

公开测试可以逐关运行，也可以一次运行六关：

```sh
python3 public_test.py --phase 2
make test
```

没有完成的关卡报错是正常的。学生仓库的 `make test` 不包含 Phase 0，教程单独测试。

### GitHub Actions 自测

模板已包含工作流。提交个人 `bomb` 后，每次 push 会自动编译解法，并分别运行正式六关和隐藏关的公开测试；pull request 和 Actions 页面中的手动运行也支持。Phase 0 教程不在 Actions 中测试，仍可在本地运行。工作流不读取 `config.txt`，不需要学号、Secrets 或其他领取配置。

到仓库的 Actions 页面打开 `BombLab public tests`，查看 `Phase 1 public tests` 至 `Phase 6 public tests`，以及 `Secret phase public tests (optional)`。某关失败时其他关仍继续测试，点开对应任务可看到失败的 seed 和错误类别。刚开始六关尚未实现，正式关卡显示失败是正常的。

隐藏关是选做题，测试失败不影响正式六关的成绩。它需要同一个 seed 下的前六行口令全部正确；日志中的 `prerequisite_` 错误表示前六关尚未通过，不是隐藏关答案本身的错误。没有完成隐藏关时，它的任务会显示失败，不会假装通过。

如果提示 `Personal bomb is missing`，说明下载的炸弹没有随代码提交。执行 `git add -f bomb` 后提交并 push。Actions 会在运行时恢复炸弹的可执行权限，不需要为了 CI 保留学号配置。

Actions 只检查公开测试，不代表最终成绩，也不代替教师的隐藏测试。

### 6. 换一个输入验证

最后，再选一个自己没有调试过的 seed 验证六关，例如：

```sh
./defuser --seed 20261023 | ./bomb --seed 20261023
```

如果只在最初的输入上成功，回到计算过程检查遗漏的分支、数据或位运算。公开测试通过也不代表隐藏测试一定满分。

## 五、实验指导

### 静态分析：先看结构，不要从头翻译到尾

`objdump` 可以在不运行程序的情况下查看汇编。先找到关卡函数，标出调用、循环、条件跳转和返回的位置，再决定哪些指令需要仔细分析。

建议边看边记：

- 哪些值来自 challenge，哪些来自你输入的口令？
- 函数调用前，参数放在哪些寄存器中？返回值后来被谁使用？
- 分支条件是什么？循环什么时候结束？
- 访问内存时，地址是怎样算出来的？字段大小是多少？

如果关卡调用了其他函数，也要跟进去看。不要只读完关卡入口函数，就假定计算已经全部看到了。

### 动态分析：用具体的值检查推测

GDB 用来验证你对汇编的理解。与其一直单步，不如先想清楚要观察哪个值，再在对应位置停下。

| 命令 | 用途 |
| --- | --- |
| `break *phase_02` | 在第 2 关函数入口设置断点 |
| `run` | 开始运行 |
| `continue` | 继续到下一个断点 |
| `disassemble phase_02` | 查看第 2 关汇编 |
| `info registers` | 查看寄存器 |
| `ni` / `si` | 执行下一条指令；`si` 会进入被调用函数 |
| `x/s $rdi` | 在关卡入口查看输入字符串 |
| `x/8gx $rsp` | 查看栈上的八个 8 字节值 |
| `p/x $rax` | 以十六进制查看寄存器值 |
| `help x` | 查看读取内存命令的用法 |

不确定表达式是否恢复正确时，找一个能走到相应分支的输入，用实际运行结果检查。一次结果相同只能说明这一次相同；分支、循环边界和不同起点也需要检查。

## 八、隐藏关

隐藏关选做，不影响正式六关的评分。

六关完成后，如果口令通过管道或文件输入，炸弹还会尝试读取第七行。终端里手动输入六行不会自动进入隐藏关。可以从 `secret_gate`、`secret_copy` 和 `secret_phase` 开始分析；求解接口见 `defuser.h` 中的 `solve_secret`。

隐藏关还会使用前六行输入得到的 context。解法完成后，可以这样验证：

```sh
{ ./defuser --seed 42; ./defuser --secret --seed 42; } | ./bomb --seed 42
```

批量检查公开 seed，可运行 `python3 secret_public_test.py`。只有炸弹输出 `Secret phase defused.` 才算隐藏关通过；仅完成前六关不算。Actions 中的隐藏关任务使用同一份脚本。

这里不要求覆盖返回地址，也不需要 shellcode。入口和校验方式留给你自己观察。
